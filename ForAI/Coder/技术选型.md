# 技术选型

> 本文档记录当前已经确认的技术方向、架构分期和待定事项。除明确固定的核心技术外，不在现阶段锁定具体第三方依赖或服务厂商。

## 1. 选型结论

### 1.1 客户端框架与语言

- 总体框架：Flutter；
- 开发语言：Dart。

选择 Flutter 与 Dart 的原因：

- 使用一套代码覆盖 iOS、Android、Windows 和 macOS；
- 适合实现高表现力的自定义 UI 与动效。

### 1.2 核心数据技术

- MVP 使用嵌入式 SQLite 作为本地数据库；
- 第二版在保留本地 SQLite 的基础上，使用 PostgreSQL 作为服务器数据库；
- 核心技术固定为 Flutter、Dart、SQLite，第二版服务器数据库固定为 PostgreSQL；
- 其他依赖尚未决定。

### 1.3 技术成熟度原则

后续依赖只选择满足以下条件的方案：

- 主流；
- 长期维护；
- 文档完整；
- 对 iOS、Android、Windows、macOS 四端支持成熟。

## 2. 平台策略

MVP 正式覆盖以下四个平台：

- iOS；
- Android；
- Windows；
- macOS。

平台实现原则：

- 移动端优先打磨；
- 桌面端保持与移动端同等的核心功能；
- 四端使用响应式布局；
- 桌面端适配键盘和鼠标操作；
- MVP 不额外开发桌面端独有功能。

## 3. 架构分期

### 3.1 MVP：本地优先、无服务器

MVP 采用本地优先、无服务器架构。SQLite 用于保存：

- 资产与负债条目；
- 快照；
- 投资日志；
- 提醒配置；
- 其他已经确认需要在本地保存的产品数据。

MVP 明确不提供：

- 登录；
- 银行、券商或理财平台 API 接入；
- 跨设备同步；
- 导入、导出或备份。

不同设备之间的数据不互通是 MVP 的已知边界。

主题系统从 Flutter 客户端开发第一天起就以可扩展方式设计，是 MVP 客户端架构的一部分，而不是交付后追加的装饰能力。首发计划支持 2 至 3 套完整主题，未来新增皮肤时不应要求重构业务模块。

### 3.2 第二版：可选云存档与智能能力

第二版继续使用本地 SQLite。用户可以自愿选择是否开启云存档；开启后，云端使用 PostgreSQL 作为服务器数据库。

第二版云端支持：

- 用户账号；
- 数据同步；
- 为未来共享资产空间与成员权限提供支持。

第二版还包括：

- AI 资产负债分析；
- AI 投资复盘；
- 图片识别辅助录入。

AI 仅用于分析和反思，不直接提供买卖建议。第二版仍不接入金融机构 API。

## 4. 关键约束

### 4.1 数据与联网边界

- MVP 数据仅保存在本地 SQLite；
- MVP 无服务器；
- MVP 无登录；
- MVP 不进行跨设备同步；
- MVP 不提供导入、导出或备份；
- MVP 与第二版均不接入银行、券商、理财平台等金融机构 API。

### 4.2 本地安全

MVP 必须具备：

- 本地数据库加密；
- 应用锁；
- 应用锁支持密码或生物识别。

具体实现库和加密方案待后续细化。

### 4.3 四端一致性

- 四端共享一套 Flutter/Dart 代码；
- 移动端优先打磨，但桌面端必须保留同等核心功能；
- 使用响应式布局适应不同屏幕尺寸；
- 桌面端必须适配键盘与鼠标；
- 不以桌面独有功能扩大 MVP 范围。

### 4.4 依赖选择约束

- 核心技术之外的依赖尚未决定；
- 不在现阶段锁定第三方状态管理方案；
- 不在现阶段锁定 ORM 或数据库访问库；
- 不在现阶段锁定动画库或图表库；
- 不在现阶段锁定云服务、OCR 或 AI 厂商；
- 后续选择必须遵循主流、长期维护、文档完整、四端支持成熟的原则。

### 4.5 主题系统约束

- 主题色、背景、插画和动效逻辑不得散落在各业务页面；
- 主题配置和主题切换能力应集中在 Flutter 客户端通用层；
- 视觉资源应按主题统一归档；
- `features/` 下的业务模块只消费统一的主题语义，不直接绑定某套皮肤的具体颜色、插画或动效实现；
- 首发支持 2 至 3 套完整主题；
- 未来扩展节日、成就或付费皮肤时，不应重构业务模块；
- 具体动画库或其他主题相关第三方依赖尚未选定。

## 5. 项目代码结构

项目采用前后端明确分离的结构。MVP 仅运行 Flutter 客户端，后端目录只为第二版能力预留。

```text
PrimitiveAccumulation/
├─ ForAI/
│  ├─ PM/
│  ├─ Designer/
│  └─ Coder/
├─ frontend/
└─ backend/
   ├─ api/
   ├─ database/
   ├─ workers/
   └─ shared-contracts/
```

不新增 `docs/` 目录，避免与现有 `ForAI/` 协作文档重复。项目结构说明继续在本技术文档中维护。

### 5.1 `ForAI/`：协作文档

保留现有职责划分：

- `PM/`：项目进度与项目管理文档；
- `Designer/`：产品设计文档；
- `Coder/`：技术架构、技术选型与代码实施文档。

### 5.2 `frontend/`：Flutter 客户端

`frontend/` 是唯一的 Flutter 客户端工程根目录，未来由同一工程覆盖 iOS、Android、Windows 和 macOS。

Flutter 工程初始化后，规划包含：

```text
frontend/
├─ lib/
│  ├─ app/
│  ├─ features/
│  │  ├─ assets/
│  │  ├─ snapshots/
│  │  ├─ growth/
│  │  ├─ investments/
│  │  └─ settings/
│  ├─ core/
│  └─ shared/
├─ test/
└─ assets/
```

各目录职责：

- `lib/app/`：应用启动、路由和主题；
- `lib/features/`：按业务模块组织功能，包括资产档案、快照、成长首页、投资日志和设置；
- `lib/core/`：本地数据库、安全、通知、UI 基础组件等通用能力，并预留集中式主题配置和主题切换能力；
- `lib/shared/`：跨业务模块复用的代码与资源；
- `test/`：客户端测试；
- `assets/`：客户端静态资源，未来按主题归档背景、插画及其他视觉资源。

`features/` 中的业务模块只消费 `core/` 提供的统一主题语义，不能散落硬编码的主题色、插画引用或动效逻辑。通过这一边界，首发 2 至 3 套主题以及未来皮肤扩展均无需重构业务模块。

当前不创建 Flutter 工程文件或上述工程内部目录，待正式初始化 Flutter 工程时再按此结构落地。

### 5.3 `backend/`：第二版云端预留

`backend/` 仅为第二版云端能力预留，MVP 不运行、不启用：

- `api/`：账号、同步、共享资产空间和 AI 请求入口；
- `database/`：PostgreSQL schema 与 migrations；
- `workers/`：AI 和 OCR 异步任务；
- `shared-contracts/`：前后端 API 契约与共享数据结构。

### 5.4 前后端数据访问边界

- MVP 中，Flutter 客户端直接访问设备本地的 SQLite；
- 第二版中，Flutter 客户端通过明确的 API 契约访问后端；
- Flutter 客户端绝不直接连接 PostgreSQL；
- PostgreSQL 仅由第二版后端访问；
- 后端具体 Web 框架、部署平台和云服务尚未选定。

## 6. 开发与发布成本

- Flutter、Dart、SQLite、PostgreSQL 等核心技术为开源免费技术；
- 发布 Apple 平台应用会产生对应的平台开发者账户费用；
- 发布 Google Play 应用会产生对应的平台账户费用；
- 第二版的云端、AI 和 OCR 能力会根据实际使用量产生费用。

具体费用以实施和发布时的平台政策及用量为准。
