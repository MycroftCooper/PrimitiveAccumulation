# MVP 本地账本与完整快照方案

本方案供实现评审。适用范围是 Flutter 客户端内的加密 SQLite。业务口径沿用[数值模型与数据字典](数值模型与数据字典.md)，用户操作沿用[更新资产近况流程](../Designer/mvp页面与用户流程设计.md)。

## 1. 从现有原型演进

[Book](../../frontend/lib/core/book.dart) 已经把每次盘点的全部条目写入 `snapshots.entries` JSON，使用整数分，提交时检查最新期号，并在同一事务中清除草稿。启动时会解码全部历史。草稿、目标、主题放在 `preferences`，每期可编辑的回顾放在 `notes`。[Entry](../../frontend/lib/core/models.dart) 已经有可跨期识别的字符串 ID。

建议保留现有期号、条目 ID、草稿恢复、提交冲突提示和回顾编辑。将已提交的数组拆为每期一行表头、每个有效条目一行明细。单期读取只需按期号取数，单项余额历史可按条目索引查询。代价是每次提交写入 N 行，N 为本期有效条目数；这样每期都能独立还原。

## 2. 建表清单

下列为建议的数据库字段。除注明可空的字段外，主键、归属、类型和金额均显式声明非空。首版默认创建一个个人空间。

| 表 | 主键及主要字段 | 写入和读取规则 |
| --- | --- | --- |
| `financial_space` | `id`，名称、类型、`base_currency` | 基准币种以空间记录为准，偏好页从此处读取。首次盘点默认人民币，与原型的元、分一致。 |
| `category` | `id`，`space_id`、`kind`、名称、排序、可空的 `parent_id` | 分类区分资产、负债，同一层级的父子须属于同一空间和类型。 |
| `financial_item` | 沿用文本 `id`，`space_id`、名称、机构、`category_id`、创建时间、可空的关闭时间 | 存当前档案与有效状态。流动性、形成来源、估值方式、利率、还款额、到期日、归属、担保物和说明按需补充。当前余额由最近一期明细读取。旧库没有的创建时间单独标明未知，可用首次出现时间作为单独的观测字段。 |
| `balance_snapshot` | `id INTEGER PRIMARY KEY`，`space_id`、`submitted_at_us`、提交当地日期、基准币种、`submission_id`、`sealed` | 保留原型微秒时间和期号；同一天可有多期。提交标识在空间内唯一，封存后的表头只读。 |
| `balance_snapshot_entry` | 主键 `(snapshot_id, item_id)`，`space_id`、`amount_minor`、`position`、当期名称、机构、资产负债类型、分类标识及名称或路径、币种 | 保存当时展示和计算所依赖的字段，包括原型已有的利率、到期日，以及用于历史分析的流动性标记等。旧回执、图表直接读本期字段。 |
| `snapshot_draft` | `space_id` 主键，`draft_id` 唯一，可空的 `base_snapshot_id`、`revision`、`changes_json` | 每个空间一份可恢复草稿。保存新增、修改、关闭操作，只改动提交中明确给出的字段。首次建档时基线为空。 |
| `snapshot_note` | `snapshot_id` 主键及外键，正文 | 单独保存可编辑的盘点回顾。改回顾不会改变任何历史金额。 |
| `wealth_goal` | `id`、`space_id`、名称、目标金额、设定日、`baseline_snapshot_id`、可选截止日、状态及完成日 | 基线引用真实快照。新建时按设定日最近一次实际提交选取；旧目标保留原有 `baseId`。 |
| `recurring_cash_flow` | `id`、`space_id`、类型、名称、金额、币种、频率、起止日期 | 保存固定收入、刚性支出和可选生活费估计。缺少估计保留缺失。 |
| `investment_decision` | `id`、`space_id`、买卖方向、日期、金额、币种、理由、可空的关联条目及复盘字段 | 日志独立写入。记录交易理由不会自动改动账面余额。 |
| `preferences` | 沿用 `key` 主键和 `value` | 保留主题、显示模式，逐步加入提醒和趋势颗粒度。目标与草稿成功迁出后才移除对应旧键。 |

**数据库约束。** 每个连接解锁后、开启事务前执行 `PRAGMA foreign_keys=ON` 并读回确认。明细到表头、明细到条目、目标到基线等使用带 `space_id` 的组合外键，父表建立完全匹配的唯一键，例如 `UNIQUE(space_id,id)`。历史引用采用 `ON DELETE RESTRICT`。索引先建 `balance_snapshot(space_id,submitted_at_us,id)` 和 `balance_snapshot_entry(item_id,snapshot_id)`，单期读取已有明细主键覆盖。[SQLite 外键说明](https://www.sqlite.org/foreignkeys.html)

**金额和币种。** 金额字段用 `INTEGER NOT NULL CHECK(typeof(amount_minor)='integer' AND amount_minor>=0)`；金额输入按十进制文本解析。人民币按分存，负债也用正数，汇总时相减。建议首版每空间只接受一种结算币种，录入异币需给出用户确认的基准币估值，有历史后不直接改币种标签。若决定支持原币分析，再扩原币金额与折算依据。[SQLite 数值精度说明](https://www.sqlite.org/floatingpoint.html)

**历史保护。** 表头以 `sealed=0` 创建，在同一事务内完成所有明细写入和校验，再置为 1。业务读查询只读取已封存的表头。用触发器拒绝修改或删除已封存表头，拒绝向已封存表头补插明细，拒绝更新、删除已有明细。仓储层对历史表只用普通 `INSERT`，禁止使用 `REPLACE`。已提交数据有误时，用户通过下一次盘点更正。

## 3. 从草稿到完整快照

1. **打开或恢复草稿。** 读取提交顺序上最新已封存期号；加载对应全量明细，再叠加草稿。保存编辑时用 `WHERE draft_id=? AND revision=?` 更新并递增版本。更新零行表示另一窗口已改动或提交，保留本窗口输入并提示刷新。首期金额、名称等在草稿中一起恢复。
2. **开始提交。** 传入 `draft_id`、当前草稿版本和基线期号。执行 `BEGIN IMMEDIATE`。先按空间和 `submission_id=draft_id` 查已封存期；若已提交，返回原期号。这使成功后重复点击或重试只产生一份快照。新的独立盘点必须生成新的草稿 ID。[SQLite 事务说明](https://www.sqlite.org/lang_transaction.html)
3. **检查版本。** 在写事务中重读持久草稿和最新期号，同时核对草稿 ID、版本及基线。过期则回滚，提示刷新后重新核对。获取写锁超时则保留草稿，可按原 ID 重试。
4. **确定本期应有的条目。** 以上期完整集合为起点，应用明确的新增、编辑与关闭。更新金额由草稿给出，未动金额沿用；用户输入零按零保存。新增条目须有明确金额。关闭从本期集合排除，先前各期保留原记录；单纯清零仍保留一行。拒绝重复 ID、编辑未知条目及互相矛盾的操作。建议首次建档至少有一项，后续关闭最后一项允许提交经用户确认的空快照，总额为零。
5. **落库并封存。** 在同一事务更新涉及的条目档案和关闭状态、插入表头、批量插入本期全部明细。提交时间只取一次，保存 UTC 微秒及当时本地日期。写完比对预期与实写的条目 ID 集合相等，检查币种、金额和每条历史展示字段，再封存表头并删除指定版本草稿。全部成功后 `COMMIT`，再刷新内存和首页；任何一步失败都 `ROLLBACK`。空明细期的统计从表头左连接，空集总额按零计算。

例如第一期有存款 10,000 元、贷款 3,000 元。第二期只把存款改为 10,500 元，数据库仍会写入两行，分别为 1,050,000 分和 300,000 分。第二期净资产 7,500 元，第一期仍为 7,000 元；即使第二期同时给存款改名，第一期仍显示当时的名称。

**读取口径。** 首页和更新基线按提交期号读取最近一次盘点。趋势按实际提交日期分组，取周期内时间最后的一期，时间相同按期号决胜。快照汇总只读本期冻结的资产负债方向与金额。计算本期变化时，上期缺失返回空。新目标选设定日最后一次真实快照；若当天又完成盘点，在同一提交事务内按同一排序更新该日新目标的基线引用。旧目标迁移时保留已有引用。旧数据只保存了时间戳，无法追溯当时的设备时区；迁移时保留原始微秒值，当地日期按迁移时设备时区推算并标记来源。

## 4. 从 JSON 账本迁移

1. 在现有加密连接内识别数据库。无业务表为新库；存在已知 `snapshots(time,entries)`、`preferences`、`notes` 结构且 `user_version=0` 时走旧库迁移。未知结构或过高版本停止写入。真实账本与内存演示账本走同一套新建逻辑。
2. 用一个写事务建新表，逐期解码旧 JSON。保留原期号、提交时间、条目 ID、数组顺序、分值及当期全部字段；同名条目不合并。历史各期分别还原。条目当前档案取最后一次出现的属性，以最后一期出现的集合标记当前有效项。历史缺失项不补行，不推测实际销户日。空字符串机构、文字利率等按原样保留，后续可由用户补齐。
3. 迁移目标及真实基线引用、每期回顾、主题和显示模式。旧草稿若存在，在当前最新期上对比并转为待提交操作；首期前的草稿转为新增操作。旧草稿没有基线或版本证据，恢复时提示核对，尤其是草稿缺少最新条目时，不自动认定为关闭；让用户选择保留或关闭。旧格式没有字段的目标状态、日期等不要虚构，保留未知及可推导字段的来源。
4. 逐期检查条目 ID 和顺序、各字段、总资产、总负债和净资产；另查回顾、目标引用、草稿和设置，执行 `PRAGMA foreign_key_check`。同一期重复 ID、损坏的 JSON 或孤立引用须中止并回滚，保留原账本可重试。核对成功才切换读写、处理旧表并在同一事务写 `PRAGMA user_version=1`。重新打开时只执行尚未完成的版本迁移。

## 5. 实施与验收

- **先交付盘点闭环。** 在 `frontend/lib/core/` 放数据库打开、建表和版本迁移，保留 `Book.saveEntry`、`Book.commit`、`Book.note` 等界面入口，再分步将按期读取改成 SQL。盘点明细、回顾、草稿和已有目标随迁移一起切换。现金流与决策日志可随对应页面在后续 schema 版本落表。
- **事务验收。** 覆盖首次建档、局部更新、显式零、关闭最后一项、同日多期、改名改分类、重复提交、旧窗口提交、草稿并发保存。模拟写到中途失败并重新打开，验证快照数、档案、草稿和旧回执均符合预期。
- **迁移和设备验收。** 用含两期同日记录、改名、目标、回顾和未提交草稿的旧格式加密库验收，并测试数据库升级失败后的重试。四个平台分别验证创建加密库、正确密钥重开、错误密钥拒绝访问、应用锁和真实设备上的异常退出恢复。内存 SQLite 事务实验仅覆盖核心写入规则。
